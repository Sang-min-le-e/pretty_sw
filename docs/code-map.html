폴더는 세 덩어리로 나뉜다

app/은 앱 전체 설정(라우터·테마·공용 위젯), core/는 화면 없는 기반 코드(네트워크·저장소·BLE), features/는 기능별 폴더다. 기능 폴더 안은 다시 presentation(화면) · data(저장소와 provider) · domain(데이터 모델) 세 층으로 나뉘고, 필요한 층만 있다.

저장하면 왜 모든 화면이 알아서 바뀌나

루틴을 저장하는 순간을 따라가 보면 이 앱의 상태 관리가 거의 다 보인다. RoutineActions가 저장한 다음 routineListProvider를 invalidate(캐시 폐기)하면, 그 provider를 watch하던 파생 provider와 화면들이 전부 다시 계산된다. 기기·템플릿·프로필 사진도 같은 모양이다.

화면 흐름

30개 경로가 이어지는 방식

유지보수

자주 할 작업 세 가지

새 화면 추가

  1. features/<기능>/presentation/에 파일 생성, 문서 주석에 Figma 노드 id
  2. app/router.dart에 GoRoute 등록 (탭 하위면 그 탭의 routes: 안)
  3. 탭 화면이면 BottomNavBar(currentIndex: n), 하위 화면이면 BackHeader

새 로컬 데이터

  1. domain/에 모델 + toMap/fromMap
  2. data/에 abstract Repository + Local…Repository(박스 이름 상수)
  3. provider 파일에 목록 FutureProvider + 저장 후 invalidate하는 Actions

로컬 → 서버 전환

  1. Api…Repository 작성 (child_repository.dart를 본보기로)
  2. …RepositoryProvider가 새 클래스를 돌려주도록 한 줄 교체
  3. 화면 코드는 provider만 보므로 그대로 둔다
정리 후보

지금 코드에서 눈에 띄는 것

  • 동작

    자동 로그인이 없다

    세션이 Hive에 남아 있어도 스플래시는 항상 /login으로 간다. 라우터에 redirect도 없다. 스플래시에서 세션 확인 후 /users/me로 분기하면 해결된다.

  • 크기

    add_routine_screen.dart 1,164줄

    추가 폼과 RoutineEditScreen이 한 파일에 있다. 반복 설정 탭, 할 일 목록 편집기를 routine/presentation/widgets/로 나누면 읽기 쉬워진다.

  • 중복

    LocalStorageService provider가 5군데

    routine, auth, devices, profile, notifications가 각자 만든다. 상태 없는 래퍼라 버그는 아니지만 core/storage/에 하나만 두는 편이 깔끔하다.

  • 위치

    apiClientProvider가 auth 안에 있다

    그래서 children이 auth를 import한다. 서버 연동 기능이 늘어나면 core/network/로 옮길 것.

  • 미사용

    쓰지 않는 패키지·API·화면

    flutter_tts, flutter_local_notifications 패키지, signup·getChildren 호출, /watch-connection 화면이 아직 아무 데서도 쓰이지 않는다.

  • 기능

    삭제가 없다

    루틴·기기·템플릿 저장소에 delete가 없다. 수정은 같은 id로 다시 put해서 덮어쓴다.

  • 테스트

    test/ 폴더가 없다

    순수 함수가 많은 new_routine.dart(toJson)와 routine.dart(fromCalendarJson)가 첫 단위 테스트 대상으로 가장 쉽다.
